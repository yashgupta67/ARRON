Email protection (anti-spoofing)

Three records tell receiving mail servers which mail really comes from ARRON:

  • SPF (in place): says Google's servers may send mail for the domain.
  • DMARC (added 28 Nov 2026): _dmarc TXT record v=DMARC1; p=quarantine; pct=25; rua=mailto:admin@arrontechnologies.com. It asks receivers to send 25% of mail that fails the checks to spam and to email daily summary reports to the admin mailbox. It starts gentle on purpose.
  • DKIM (not yet switched on): a digital signature on outgoing mail. Turn it on in the Google Admin console under Apps → Google Workspace → Gmail → Authenticate email, then add the DNS record Google shows.
Next step for email: after DKIM is on and a few weeks pass with no problems in the DMARC reports, raise pct to 100, and later change p=quarantine to p=reject.
Why this matters for hosting: email and website use different DNS records. The website records (A and www) were changed on 27 November 2026. The mail records (MX and the SPF text record) were deliberately left untouched, so email kept working throughout.

6How the site was put online, step by step

A. Finding where the domain lives

  1. Checked the public registry (RDAP). It showed arrontechnologies.com was registered on 22 Nov 2026, registrar Wix.com Ltd., name servers at Wix, and mail records at Google. This proved the domain was at Wix, not GoDaddy, so all DNS changes had to be made in Wix. 
    curl -s "https://rdap.verisign.com/com/v1/domain/arrontechnologies.com"
dig +short arrontechnologies.com MX
    Why: DNS can only be edited where the domain's name servers are hosted. Checking first avoided editing the wrong account.
  2. Found the right Wix account. The first account opened had no ARRON domain. The correct account listed arrontechnologies.com under Domains as "Not assigned to a site", so there was no Wix website to disconnect.
    Why: if a Wix site is connected to a domain, Wix locks the website records. Here nothing was connected, so the records could be edited directly.

B. Editing DNS in Wix (done through the browser, 27 Nov 2026)

  1. Opened Domains → arrontechnologies.com → Manage DNS records and checked the existing records, including the five Google MX records, which were left alone.
  2. Edited the three existing A records to 185.199.108.153, 185.199.109.153 and 185.199.110.153, then added a fourth A record, 185.199.111.153. Wix shows a warning that changing default A or CNAME records can take a Wix site offline, which is expected because the domain is moving off Wix.
  3. Edited the www CNAME from cdn3.wixdns.net to yashgupta67.github.io.
  4. Verified that the records were live on Wix's own name server and on public resolvers: 
    dig +short @ns2.wixdns.net arrontechnologies.com A
dig +short @8.8.8.8 arrontechnologies.com A
dig +short www.arrontechnologies.com CNAME
    Why: asking the authoritative server directly proves the change was saved. Asking public resolvers (8.8.8.8 is Google's) shows whether it has spread across the internet.

C. Telling GitHub about the domain (terminal, GitHub CLI)

  1. Added a file named CNAME to the repository root containing the domain, and pushed it. 
    printf 'arrontechnologies.com\n' > CNAME
git add CNAME
git commit -m "Add custom domain arrontechnologies.com"
git push
    Why: GitHub Pages reads this file to know which domain the site should answer for. It also stops the setting being lost on a future publish.
  2. Set the custom domain in the Pages settings through the GitHub API: 
    gh api -X PUT repos/yashgupta67/ARRON/pages -f cname=arrontechnologies.com
    Why: this switches on the custom domain and starts GitHub's automatic HTTPS certificate request. It was done after DNS was ready so the existing address did not break first.
  3. Waited for the HTTPS certificate to move from "authorization pending" to "approved" (about a minute), then enforced HTTPS: 
    gh api repos/yashgupta67/ARRON/pages --jq '.https_certificate.state'
gh api -X PUT repos/yashgupta67/ARRON/pages -F https_enforced=true
    Why: HTTPS encrypts the connection (the padlock) and is expected by browsers. Enforcing it redirects http:// to https:// automatically.
  4. Tested the live site by asking GitHub's server directly, which avoids stale DNS on the testing computer: 
    curl -s --resolve arrontechnologies.com:443:185.199.108.153 https://arrontechnologies.com/ | grep -o "<title>[^<]*"
curl -s -o /dev/null -w "%{http_code}\n" https://arrontechnologies.com/
    Result: HTTP 200 and the correct page title.

Result: https://arrontechnologies.com serves the ARRON site, https://www.arrontechnologies.com redirects to it, and the old address (yashgupta67.github.io/ARRON) now forwards to the new domain.

7Why the site did not open on one laptop, and the fix

Right after the change, the site opened for some people but not others. The cause was not the website. DNS answers are saved ("cached") by routers and internet providers for the record's lifetime, which Wix set to 1 hour. A home router that had saved the old Wix addresses kept handing them out, so that laptop saw a Wix "This domain isn't connected to a site" page. Public resolvers such as Cloudflare (1.1.1.1), Google (8.8.8.8) and Quad9 (9.9.9.9) already had the new addresses.

Commands that were used on the laptop (macOS)

CommandWhat it doesSafe?
networksetup -setdnsservers Wi-Fi 1.1.1.1 9.9.9.9Makes the Wi-Fi connection ask Cloudflare and Quad9 for website addresses instead of the home router.Yes. Only changes which lookup service Wi-Fi uses. Undo with the command below.
networksetup -getdnsservers Wi-FiShows the current setting. Prints 1.1.1.1 and 9.9.9.9 when the change is active.Yes, read-only.

The setting can reset when the Wi-Fi reconnects. If the Wix page returns, re-run the "get" command to check it and set it again. A router restart or simply waiting (up to a few hours) also clears the stale copy. This only affects people whose network cached the old records during the first hours.

Commands used:

Recommended extra safeguards

  • Turn on two-factor authentication for the GitHub account and the Wix account. A stolen password is the real risk, not the public repository.
  • Never put passwords, keys or private documents in the repository, since everything in it is public.
  • Do not add collaborators unless they need to publish changes. Review the list under Settings → Collaborators from time to time.
  • This documentation page is published with the site (at /documentation/) and is marked "noindex" so search engines are asked not to list it, but anyone with the link can read it. It deliberately omits passwords, account emails, card details and invoice numbers.

9Site security

The site is a set of static files. There is no database, login, server code or admin area, so there is very little to attack. The realistic risks are someone taking over an account (GitHub, Wix, Google) or faking email from the domain, so those are covered below as well as the site itself.

10Search visibility (SEO)

Nobody can guarantee a top ranking, because Google decides. Searches for the brand ("arron technologies") are realistic to win within weeks once Google has indexed the site. Broad searches such as "AI services" are very competitive and take months and links from other sites. Local searches such as "AI services Dallas" are the realistic target.

What still has to be done by the account owner

  1. Google Search Console (search.google.com/search-console): add arrontechnologies.com as a domain property, verify it with the DNS TXT record Google provides, then submit https://arrontechnologies.com/sitemap.xml. This asks Google to index the site and shows any problems.

12How to change the website later

The pages are generated by a small Python script so the design stays consistent across all pages.

  1. Edit the content in _src/build.py (page text) or assets/styles.css (design).
  2. Rebuild the pages from the project folder: 
    python3 _src/build.py
  3. Publish by committing and pushing: 
    git add -A
git commit -m "Describe the change"
git push
    GitHub Pages republishes automatically, usually within one or two minutes. Hard-refresh the browser (Cmd+Shift+R) to see it.

The build also regenerates sitemap.xml, robots.txt, 404.html and .well-known/security.txt automatically. Team photos are in assets/img/team/, general photos in assets/img/photos/, partner logos in assets/img/partners/ and the logo files in assets/img/.

13Maintenance checklist

  • Monthly: Wix charges $27.27 for the three mailboxes on the 22nd (plus any taxes). Keep the payment method valid or the email will stop.
  • Before November 2029: renew the domain in Wix (Domains → arrontechnologies.com). Consider turning on auto-renew. If the domain lapses, both the website and the email stop.
  • Never delete the MX or SPF records in Wix DNS: that breaks email.
  • Never change the Wix name servers without a plan for DNSSEC.
  • Never delete the CNAME file in the repository: it holds the custom domain setting.
  • After any Wix or LinkedIn session, sign out, especially on shared computers.
  • Email protection: switch on DKIM in Google Admin, then tighten DMARC from 25% to 100% and later to reject (section 3).
  • Search: add the site to Google Search Console and Bing, and submit the sitemap (section 10).
  • Two-factor sign-in: switch it on for GitHub, Wix and Google if not done yet.
  • Do not add outside scripts to the site without updating the content security policy (section 9).
  • Still to decide: a contact form that stores messages needs a service such as Formspree or Mailchimp, because the site has no server. Today the forms open an email draft.
